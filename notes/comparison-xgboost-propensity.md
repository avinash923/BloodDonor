# Comparison: donor return-propensity models (EXP-11)

Source of numbers: `reports/xgboost_propensity/` (generated by
`experiments/exp11_xgboost_donor_propensity.py`, 5 × 5 repeated stratified CV,
tuning and calibration nested inside each outer fold).

## Problem framing

The goal is to predict, for each donor using the app, how likely they are to donate again.

* **Kaggle availability data (exp2), rejected.** Every model scored held-out ROC-AUC 0.47–0.51.
  The label is not predictable from its features, so no amount of tuning would help. Training
  XGBoost on it would produce a model that only looks real.
* **UCI Blood Transfusion Service Center, chosen.** Real donor records (748 donors, Hsin-Chu City,
  Taiwan), published with a peer-reviewed paper (Yeh et al., 2008). The label is whether the donor
  donated in March 2007. The features are Recency, Frequency and Time, which this app can compute
  for its own users.
  The UCI and OpenML hosts are blocked from the build environment. The file came from PyCaret's
  GitHub mirror and is accepted only if it reproduces the published row count, positive count and
  a content checksum.

## Variants and what each one showed

| Variant | Idea | ROC-AUC | Brier skill | Verdict |
|---|---|---|---|---|
| `prior` | constant 23.8 % | 0.500 | 0 | Reference |
| `bernoulli_rate` | Unconventional: a single feature, donations per month (F/T), after the paper's Bernoulli-sequence view | 0.717 ± 0.030 | 0.054 | Ranks well but calibrates poorly. Recency carries signal it ignores. |
| `logistic_rfmt` | Log-engineered RFMT plus logistic regression | 0.753 ± 0.037 | 0.151 | Strong, simple baseline |
| `xgb_repo_default` | `configs/ml_models.yaml` defaults: depth 6, 300 trees, scale_pos_weight 3 | 0.680 ± 0.043 | **−0.143** | Overfits 748 rows. `scale_pos_weight` distorts probabilities, so it scores worse than predicting the base rate. |
| `xgb_tuned` | Engineered features, nested randomised search on log loss | 0.753 ± 0.039 | 0.157 | Matches LR |
| `xgb_mono_platt` (**deployed**) | `xgb_tuned` plus monotone constraints plus Platt calibration | 0.749 ± 0.036 | 0.154 | Matches LR, with domain-consistent shape |

Corrected resampled t-tests (Nadeau–Bengio):

* `xgb_mono_platt` vs `logistic_rfmt`: ΔAUC −0.004, p = 0.77.
* `xgb_mono_platt` vs `xgb_tuned`: ΔAUC −0.004, p = 0.68.
* `xgb_mono_platt` vs `xgb_repo_default`: ΔAUC +0.070, p = 0.002. ΔBrier −0.054, p < 0.001.

## Conclusions

1. **Tuning mattered more than the algorithm choice.** Untuned XGBoost was the worst informative
   model. Shallow trees, strong `min_child_weight` and a log-loss objective fixed it.
2. **On this data, XGBoost does not beat logistic regression.** Four features and 748 rows leave
   little non-linearity to exploit. The deployed XGBoost model is therefore no more accurate than LR.
   It was chosen because XGBoost was requested and because it costs nothing in accuracy.
3. **Monotone constraints cost nothing measurable.** They stop the model from learning that donating
   more often lowers return probability. A small, noisy dataset can produce that kind of artefact.
4. **Expected performance for users:** ROC-AUC ≈ 0.75 (± 0.04 across folds). This is useful for
   ordering donors by likelihood. It is weak for yes/no decisions about individuals.

## Integration decision

The model output is exposed as `donation_propensity`:

* in donor profiles, with the inputs and a meaning statement;
* in recruitment candidate lists, as an advisory value only.

It is **not** fed into UDI or the invitation order. The UCI label measures voluntary return
donation, not response to an emergency invitation, and `udi_engine.DonorCandidate` explicitly
forbids using a UCI behaviour score there.

## Ideas for next experiments

* Log real invitation outcomes (accepted/declined/expired) and train a response model on those.
  That is the label UDI actually needs. The UCI model could serve as a prior or feature.
* Calibrate against the local population before trusting absolute probabilities. A Taiwan-2007
  base rate (23.8 %) will not transfer as is.
* Survival / time-to-next-donation modelling (e.g. discrete-time hazard on donation histories) once
  the app accumulates longitudinal records.
* Compare against a Bayesian Beta-Geometric/NBD "buy-till-you-die" model, which is designed for exactly
  RFM-style repeat behaviour.
